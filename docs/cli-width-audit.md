# CLI 超宽行治理方案（超宽行清单 + 候选策略 + 拍板清单）

> 任务：t39（**只出方案，不改产品代码**）。用户反馈「CLI 输出换行、疑似超出终端边界」，
> 本文件给出 80/100/120 列 pty 的**实测**清单、候选策略对比与「需拍板 / 可直接修」分类。
> 复现脚本见 §5（照抄即可重跑，结论可验证，不是估算）。

---

## 0. 结论摘要

1. **实测**：在 80/100/120 列 pty 下，超宽行集中在四类——**标题行**（103 列，80/100 都折）、
   **v3 信息行**（元信息 112~116、分P清单 227、预计大小 126~161，三种宽度全折）、
   **事件行**（常规最长 117~141；`--debug` 的 `GET`/`Response` 行最长 **716**）、
   **URL 行**（`--print-urls`，**669** 列）。
2. 同一批实测里，**流表行、进度行、侧车行一条都没超宽**——宽度契约（`download.layoutCells`
   按 `TerminalWidth` 省列、进度帧按宽度收缩）在这三类上是生效的。缺宽度处理的是
   **人类信息行与诊断/机器行**，不是排版引擎。
3. **推荐组合**：① v3 信息行 → **按显示宽度夹取**（分P清单每项标题夹取、预计大小只留文件名、
   元信息夹取可变段），保持「一行一条信息」；② 标题行 → **折行 + 续行缩进 28**（不丢字，
   标题是用户核对是否下对稿件的唯一凭据）；③ `--debug` 的 `GET`/`Response` 长行 →
   **截断 + 省略号**（细节进日志文件）；④ `--print-urls` 的 URL 行 → **不动**（机器契约）；
   ⑤ 事件行时间戳压缩（28→13 列）**不推荐**（收益小、影响所有事件行的既有观感）。
4. 「需用户拍板」的是**默认观感**上的取舍：标题行（夹取 vs 折行）、事件行正文是否折行/截断、
   时间戳是否压缩、是否引入**通用折行**（可能影响脚本按行解析）。其余（`--debug` 长行、
   v3 信息行的宽度夹取）可视为缺陷修复直接做——它们在**任何终端**上都会折行。

## 2. 候选策略

### 2.1 策略 1：截断 + 省略号（按显示宽度夹取）

- **怎么截**：在**纯文本阶段**（上色之前）按显示宽度切，末尾补「…」；前缀（时间戳/缩进）不参与裁剪。
- 分段的取舍（关键：**哪些段可以丢**）：

| 行 | 建议裁剪对象 | 理由 |
|---|---|---|
| 标题行 | 标题段 → `cols-37-1` 列 | 标题是内容，截了就找不回；但这是唯一不破坏「一行一事件」的做法 |
| 元信息行 | `发布 … · 分P N` 段整体丢弃 | UP主/BV 号是识别项；日期与分P数在分P清单里也有 |
| 分P清单行 | 每项标题夹到固定列（如 16 显示列），整行再兜底夹取 | 它是**索引**（P几 + 大致内容），不是内容本体 |
| 预计大小行 | `输出:` 只留**文件名**（`filepath.Base`），仍超宽再夹 | 目录名通常就是标题本身，重复且最长 |
| 字幕清单行 | 逐项夹到固定列，优先保留语言短名 | 语言码是识别项，短名是补充 |
| 事件行 | 正文尾部夹取（保留头部） | 头部是动作/错误码，尾部通常是长路径或长 JSON |
| URL 行 | **不裁** | 机器契约：URL 必须完整可复制 |

- 优点：一定一行一条，脚本按行解析不受影响；实现最简单（一个 `clampDisplay(s, w)`）。
- 缺点：丢信息（用户可能想复制完整标题去搜索/分享）。

### 2.2 策略 2：折行 + 续行缩进

- **怎么做**：按显示宽度在词/标点边界折成多行，续行加 28 列缩进（与信息行对齐基准一致）；
  折行必须在**上色之前**做，否则会切断 ANSI 序列（仓内现有渲染是先拼彩色整串，需要改造）。
- 优点：不丢信息；视觉上仍是「一个条目」（续行缩进让折行读起来不像新事件）。
- 缺点：① 破坏「一行一事件」——`grep`/`awk` 类脚本会看到多出来的行（**这是需要拍板的点**）；
  ② 终端原本也会自动折行，折行只是把「折在哪」变得可控；③ 需要 ANSI 安全 + 宽字符安全的分词器。
- 变体：只对**标题行**折行（信息行用夹取），把影响面收窄到一行。

### 2.3 策略 3：事件行时间戳压缩

- **怎么做**：28 列的时间戳压成 `[22:19:23.4] `（13 列）→ 每条事件行释放 15 列；
  同时要改 v3 信息行的 28 列缩进基准。
- 优点：一次性给**所有**人类行腾出 15 列；实现小。
- 缺点：① 改的是**默认观感**（上游契约里最显眼的一项）；② 跨天运行丢日期、排障丢毫秒；
  ③ 信息行的 28 列对齐要跟着改，等于同时动两处既有观感；④ 收益只有 15 列，救不了 227 列的分P清单。
- **不推荐**。

## 3. 与「默认观感 = 上游契约」的关系（拍板分类）

### 3.1 既有契约怎么说

- `CHANGELOG` 2.12.8 与既有文档写明：**事件行不参与宽度契约**（与上游 C# 一致）——只有
  **流表行/进度行**受宽度约束（`internal/download` 的 `layoutCells`/`prefixWidth` 与对应用例）。
- 也就是说：事件行超宽**在今天不算违约**；但 **v3 信息行（2.15.0 引入的自研观感）** 与
  「标题行折行」不在任何既有契约里——空白处既可以按缺陷修，也可以按新观感设计，
  取决于是否要改用户默认看到的输出。

### 3.2 需用户拍板（改默认观感 / 影响脚本）

| 项 | 为什么必须拍板 | 我的建议 |
|---|---|---|
| 标题行：夹取 vs 折行 | 两者都改可见输出；折行破坏「一行一事件」 | **折行 + 续行缩进**（不丢字）；若更看重「一行一条」则改夹取 |
| 事件行正文是否折行/截断 | 影响所有事件行，脚本可能按行取数据 | 只对**超阈值的诊断行**（`--debug`）截断；常规事件行保持原样 |
| 时间戳是否压缩（策略 3） | 直接改默认观感的两处（时间戳 + 28 列缩进基准） | **不做** |
| 是否引入通用折行（所有人类行） | 影响面最大，可能破坏外部脚本 | 不做；按行类型分别处理 |
| 字幕清单的多语言夹取策略 | 匿名环境**没有实测数据**（登录后补测） | 先按逐项夹取实现，登录后补一条真机用例 |

### 3.3 可直接修（判为缺陷 / 自研布局补完，不动上游契约）

| 项 | 依据 |
|---|---|
| `--debug` 的 `GET`/`Response` 长行截断（716/248 列） | 诊断输出，不是默认观感；完整内容应进 `--debug` 日志文件（已有该机制），终端只留摘要 |
| 分P清单行每项标题夹取（227 列） | v3 是**自研**布局（2.15.0），概念图上是窄例；227 列在任何终端都折行 = 实现没覆盖宽度 |
| 预计大小行只显示文件名（161 列） | 同上；目录段与标题重复，删它不丢识别信息 |
| 元信息行夹取（116 列） | 同上；丢弃的 `发布/分P` 段在别处仍可见 |
| URL 行保持不变 | 机器契约（可复制性）优先于宽度 |
| 流表行/进度行/侧车行 | 已达标（表 A #8），新增用例里继续兜住 |

> 判断口径：**「任何终端都会折行、且行本身是自研布局」→ 可直接修**；
> **「改了就改变用户默认看到的既有观感（上游契约）或影响机器/脚本解析」→ 需拍板**。

## 4. 推荐方案与工作量

### 4.1 推荐组合（分两步走）

**第一步（可直接修，不等拍板）**：
1. 新增 `clampDisplay(s string, w int) string` 与 `wrapDisplay(s string, w int, indent int) []string`
   （纯文本阶段、宽字符与组合字符安全、不切断 ANSI）；
2. v3 信息行接入夹取：分P清单每项标题、预计大小（只留文件名）、元信息（末尾段可丢）、字幕清单（逐项）；
3. `--debug` 的 `GET`/`Response` 行截断 + 指向日志文件的提示；
4. 用例：宽度边界（恰好 = cols / cols-1 / cols+1）、宽字符与 emoji、ANSI 不被切断、
   既有 v3 逐字用例在**未超宽**输入下保持不变（只有超宽才触发夹取）+ 变异验证。

**第二步（等拍板）**：
5. 标题行按拍板结果实现（折行续行缩进 或 夹取）；
6. 若拍板要改时间戳/通用折行，再动 `util` 的时间戳格式与缩进基准（并同步 §1.2 的预算表）。

### 4.2 工作量

| 项 | 内容 | 估计 |
|---|---|---|
| W1 | `clampDisplay` / `wrapDisplay`（宽字符 + 组合字符 + 不切 ANSI） | 0.25~0.5 人日 |
| W2 | v3 信息行接入（分P/预计大小/元信息/字幕） | 0.5 人日 |
| W3 | `--debug` 诊断行截断 + 日志提示 | 0.25 人日 |
| W4 | 用例与变异（边界/宽字符/ANSI/既有逐字用例不回归） | 0.5 人日 |

| W5 | 标题行（折行或夹取，拍板后） | 0.25 人日 |

## 5. 复现方法（照抄可重跑）

pty 里跑 CLI 并按显示宽度逐行判定（本文件的实测数据就是这么来的）：

```python
import os, pty, struct, fcntl, termios, signal, re, time, select, unicodedata

def run(cols, argv):
    pid, fd = pty.fork()
    if pid == 0:
        e = dict(os.environ); e['COLUMNS'] = str(cols); e['TERM'] = 'xterm-256color'
        os.execvpe(argv[0], argv, e)
    fcntl.ioctl(fd, termios.TIOCSWINSZ, struct.pack('HHHH', 40, cols, 0, 0))
    os.kill(pid, signal.SIGWINCH)
    out = b''; end = time.time() + 300
    while time.time() < end:
        r, _, _ = select.select([fd], [], [], 0.5)
        if not r:
            if os.waitpid(pid, os.WNOHANG)[0]: break
            continue
        try: chunk = os.read(fd, 1 << 16)
        except OSError: break
        if not chunk: break
        out += chunk
    return out.decode('utf-8', 'replace')

ANSI = re.compile(r'\x1b\[[0-9;?]*[ -/]*[@-~]')
def width(s):
    return sum(0 if unicodedata.combining(c) else (2 if unicodedata.east_asian_width(c) in 'WF' else 1) for c in s)

for cols in (80, 100, 120):
    raw = run(cols, ['/tmp/bb3', '-I', 'BV1B58d6PEXz'])           # 标题行 + 流表
    # raw = run(cols, ['/tmp/bb3', '--sub-only', 'BV1NCHf6eE6j'])   # v3 信息行（多P）
    # raw = run(cols, ['/tmp/bb3', '--print-urls', 'BV1B58d6PEXz']) # URL 行
    for line in re.split(r'[\r\n]', raw):
        vis = ANSI.sub('', line)
        if vis.strip() and width(vis) > cols:
            print(cols, width(vis), vis[:120])
```

本次实测的五组命令与超宽行数：

| 场景 | 命令 | 超宽行数（80 / 100 / 120） |
|---|---|---|
| A 单P 只解析 | `bbdown -I BV1B58d6PEXz` | 2 / 1 / 0 |
| B 多P 下载路径（`--debug`） | `bbdown --sub-only --debug BV1NCHf6eE6j` | 44 / 34 / 22 |
| B2 同上（无 `--debug`） | `bbdown --sub-only BV1NCHf6eE6j` | 13 / 4 / 4 |
| C 直链 | `bbdown --print-urls BV1B58d6PEXz` | 6 / 3 / 3 |
| D 真下载（音频） | `bbdown --audio-only --skip-mux BV1B58d6PEXz` | 6 / 3 / 1 |
| E 多P 只解析 | `bbdown -I BV1NCHf6eE6j` | 2 / 0 / 0 |

## 6. 边界与未做的事

- **未实测**：登录态的字幕清单行（匿名拿不到字幕，见 t36）；`--info-json` / `--progress-json`
  的输出（机器契约，一行一条 JSON，**本就不参与宽度契约**）；Windows 终端（conhost）的折行
  行为与 ANSI 支持（折行实现要单独考虑，属拍板后的实现细节）。
- **未改任何产品代码**（本任务只读 + 出文档）。
- 宽度口径 = 东亚宽度（全角 2 列），与仓内 `download.DisplayWidth` 同规则。
